# Version 1: Code-level CQRS and the Pain of State-based CRUD

## 1. V1 Design
Based on the initial idea, the V1 architecture of the `corebank` service was implemented. Looking at the source code, the system appears very "clean" and adheres to the CQRS pattern at the application level:
- **Command (Write):** Organized under `handler/command`. For example, `TransferCommandHandler` handles the transfer logic, debiting the sender and crediting the receiver.
- **Query (Read):** Organized under `handler/query`. For example, `GetAccountBalanceQueryHandler` simply retrieves the balance for display.

The code structure is excellent, but the **Data structure** remains a traditional CRUD (Create, Read, Update, Delete) model. Both Command and Query hit the same unified Database, interacting with a single `Account` table containing a `balance` column.

## 2. How V1 Handles Transactions and Its Bottlenecks
To prevent Double-spending, V1 relies entirely on Database Locking mechanisms. In `TransferCommandHandler`, the system operates as follows:
```java
// Lock in deterministic order to reduce deadlock risk.
Account first = lock(firstId); // Executes SELECT ... FOR UPDATE
Account second = lock(secondId);

source.debit(request.getAmount());
destination.credit(request.getAmount());
transactionCommandService.save(...);
```

### Pain Point 1: Database Bottleneck & Deadlocks
Using `SELECT ... FOR UPDATE` (Pessimistic Lock) forces the Database to lock specific rows. When thousands of transactions pour in simultaneously, threads must wait in line for the row locks to be released. The system becomes extremely sluggish. Furthermore, having to write custom logic to "sort IDs to prevent deadlocks" is a clear sign that the Database is being forced to do things beyond its capabilities in a distributed environment.

### Pain Point 2: CRUD Breaks Accounting (Ledger) Principles
A real banking system is fundamentally a **Ledger**. An accountant never uses an eraser to wipe out an old number and write a new one over it. 
Yet, V1 does exactly that: `source.debit()` essentially fetches the old balance, subtracts the amount, and **Overwrites (UPDATEs)** the Database. 
- We lose the "Source of Truth" of the past. 
- All audit history is temporarily patched through the `BankTransaction` table. If the Account table and Transaction table drift out of sync (due to a bug or manual DB intervention), no one knows which number is actually correct.

### Pain Point 3: "Half-baked" CQRS
CQRS in V1 is only separated at the **Code Logic** layer, not the **Data** layer. When there is a massive spike in users checking their balances (Queries), they compete for Database resources with the money transfer flows (Commands), dragging the entire system's performance down.

## V1 Conclusion
V1 successfully solved the functional requirements (it runs), but it completely failed as a high-performance, absolutely secure banking system design. We need a massive paradigm shift. (Continue to `v2.md`)
