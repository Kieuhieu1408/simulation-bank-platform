Corebank V2:
True CQRS + Event Sourcing

Refactoring the Core Banking service from State-based CRUD to an Event-Sourced, dual-database architecture — eliminating pessimistic locks, adding Actual vs Available balance, and building a proper audit ledger.

📅 2026-09-27 ✍️ Hieu Quoc Kieu 🟢 Compile: PASS 📦 Spring Boot 4.1 · Java 25 · Oracle
V1 Pain Points WHY REFACTOR

V1 had CQRS at the code layer only — both Command and Query still hit the same database table. Three structural problems made this untenable at scale.

🔒
Pessimistic Lock Bottleneck

SELECT … FOR UPDATE on two account rows. Threads serialize. Deadlock risk grows with TPS. Even required custom ID-sort logic to avoid it.

🗑️
CRUD Destroys Audit History

account.debit() overwrites the balance column. The past is gone. If the DB drifts from the transaction table, there is no ground truth to recover from.

🪣
One Balance for Two Purposes

A single balance column cannot represent a pending deduction. Double-spending window exists between transfer initiation and confirmation.

V2 Architecture DUAL DATABASE

Write and Read are now fully separated — different tables, different responsibilities, different optimization targets.

AccountAggregate IN-MEMORY

AccountAggregate is not a JPA entity. It lives purely on the JVM heap, reconstituted by replaying events. Validation happens at RAM speed — no DB round-trip needed to check balance.

// V1 — DB lock + mutate column
Account source = accountRepo.findByIdForUpdate(id);  // SELECT FOR UPDATE 🔒
source.debit(amount);                                  // UPDATE balance column ✏️

// V2 — RAM validation + append event
AccountAggregate source = eventStore.load(id);       // Snapshot + Replay on RAM ⚡
source.reserveFunds(amount, currency, transferId);    // Validates availableBalance 🧠
eventStore.append(source);                             // INSERT event — no lock needed ✅
Event Store CORE ENGINE

EventStore is the central Write Side engine. load() reconstitutes an aggregate; append() persists new events and records them in the Outbox — all in a single DB transaction.

// EventStore.append() — atomically writes Event + Outbox

AccountProjector READ SIDE SYNC

The Projector listens to Domain Events and keeps account_view and transaction_history_view in sync. It runs in the same DB transaction as EventStore.append(), so Write and Read are always consistent — no eventual consistency delay in this phase.

@EventListener
@Transactional
public void on(FundsReservedEvent event) {
    AccountView view = accountViews.findById(event.aggregateId())...;

    view.reserveFunds(event.amount(), event.version());  // idempotency guard inside ✅
    accountViews.save(view);

    historyViews.save(new TransactionHistoryView(..., "DEBIT", view.getAvailableBalance()));
}

The last_event_version guard inside each mutator ensures that if Kafka delivers the same event twice in future, the projector silently skips it — no double deduction.

Actual vs Available Balance ANTI DOUBLE-SPEND

The key mechanism that prevents double-spending without row-level locking.

  Transfer 500K: A → B
TransferCommand received
Load AccountAggregate A from Event Store. Check availableBalance >= 500K on RAM.
FundsReservedEvent → A
Projector: available_balance −= 500K. Actual stays. App shows deduction immediately. A cannot spend this 500K elsewhere.
FundsDepositedEvent → B
Projector: actual_balance += 500K, available_balance += 500K. B's money is live.
TransferCompletedEvent → A
Projector: actual_balance −= 500K. Ledger closes. Transaction officially settled.
TransferFailedEvent → A (if B fails)
Projector: available_balance += 500K. Funds released. A can use them again.
Transfer Flow (Saga) COMMAND HANDLER V2

The new TransferCommandHandler has no locks, no ID sorting, no manual idempotency check. Concurrency is handled by the DB constraint. Failures auto-retry up to 3 times.

for (int attempt = 1; attempt <= MAX_RETRIES; attempt++) {
    try {
        AccountAggregate source = eventStore.load(request.getSourceAccountId());
        source.reserveFunds(amount, currency, transferId);     // validate on RAM

        AccountAggregate dest = eventStore.load(request.getDestinationAccountId());
        dest.depositFunds(amount, currency, transferId);

        source.completeTransfer(amount, currency, transferId, destId);

        eventStore.append(source);   // INSERT + Outbox — no locks
        eventStore.append(dest);

        return response;
    } catch (DataIntegrityViolationException ex) {
        // Optimistic lock conflict → retry
        if (attempt == MAX_RETRIES) throw ex;
    }
}

Trade-offs Accepted HONEST COSTS
⚡
Eventual Consistency (Phase 1: None)

In this phase, the Projector runs synchronously in the same transaction. Zero delay. When we move to Kafka, a brief sub-second lag will appear — manageable with optimistic UI updates.

📸
Snapshotting Complexity

Without snapshots, replaying 1M events would crash RAM. The SnapshotPolicy triggers every 50 events. Added complexity, but correctness is unaffected if snapshot fails.

🧩
Event Schema Evolution

Events are immutable once written. The schema_version column + upcasters handle format changes. Old events must always deserialize correctly — test coverage is critical.

What Does NOT Change
  • ✓ REST API surface — same endpoints, same contract
  • ✓ Security — Keycloak / OAuth2 Resource Server
  • ✓ Outbox infrastructure — OutboxRecorder, OutboxDispatcher
  • ✓ Idempotency infrastructure — IdempotencyRecord, IdempotencyService
  • ✓ Observability — Prometheus, OTLP tracing, Loki
  • ✓ Flyway baseline — V1–V4 migrations untouched
