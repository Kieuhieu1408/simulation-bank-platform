# Version 2: Evolution with True CQRS and Event Sourcing

Arising from the bottlenecks and data loss risks of V1, the V2 architecture was born as a revolution for the Corebank. The missing puzzle piece to make CQRS perfect is **Event Sourcing (ES)**.

## 1. V2 Design: Breaking the CRUD Monopoly
V2 applies **True CQRS**: Completely segregating the Database of the Write Side from the Read Side.

### Write Side (Event Store)
*   **No more Balance column:** The Write Side Database (usually Postgres, Oracle, or EventStoreDB) no longer has an `Account` table to store states. It only contains a `DOMAIN_EVENTS` table.
*   **Append-Only Ledger:** Every money transfer transforms into events: `AccountCreated`, `FundsReserved`, `TransferCompleted`. The Database only performs Insert operations, adding these events to the end of the log. `UPDATE` or `DELETE` commands are strictly prohibited.
*   **Breaking Bottlenecks with Optimistic Locking:** We no longer use `SELECT FOR UPDATE`. The Database controls concurrency using an optimistic lock constraint: `UNIQUE(aggregate_id, version)`. Business calculations (checking balances, debiting) happen entirely **In-Memory** by replaying old events. As a result, Validation and Write speeds are tens of times faster.

### Read Side (Projections)
*   **Second Source of Truth for Display:** Events generated from the Event Store are pushed through Kafka or an Internal Event Bus.
*   **Projectors (Synchronizers):** Listeners catch these events, calculate the final number, and `UPDATE` a separate Database (used solely for Queries).
*   **Blazing Fast Queries:** In this Read Database, the `account_view` table returns with its `balance` column. When users open the App to check their balance, they query straight into this table without affecting the performance of the Transfer flow (Write Side).

## 2. Pending Transactions and Anti Double-Spending with Saga
In V1, a single transaction carried the burden of debiting Person A and crediting Person B simultaneously. In V2 (a true distributed system), we use the **Saga Pattern** and split the balance into two columns in the Read DB:
1.  **Actual Balance (Ledger Balance):** The actual money residing in the bank.
2.  **Available Balance:** The money the user is currently permitted to spend.

**Flow of transferring $500 from A to B in V2:**
1.  **Command (At A):** Check In-Memory, confirm `Available Balance >= $500`. Generate a `FundsReservedEvent($500)` and save it to the Event Store.
2.  **Projector:** Catches the event, subtracts $500 from the `Available Balance` column in A's Read DB. *(A's App immediately shows the deduction. A cannot spend this $500 elsewhere. Double-spending is successfully prevented).*
3.  **Saga Orchestrator:** Calls service B / account B. B is successfully credited with $500.
4.  **Command (At A):** Generates a `TransferCompletedEvent($500)`.
5.  **Projector:** Subtracts $500 from the `Actual Balance` column in A's Read DB. The transaction is officially closed.
*(If step 3 fails, A generates a `TransferFailedEvent`, and the Projector refunds the $500 back to A's `Available Balance`).*

## 3. Trade-offs to Anticipate
V2 brings the capabilities of a true "tech unicorn," but the engineering team must accept the costs:
*   **Eventual Consistency:** There is a millisecond delay between the Write Side and the Read Side. The Frontend (App/Web) needs smart UX solutions to hide this delay (e.g., WebSockets or temporary local UI updates).
*   **The Snapshotting Crisis:** If an account has 1 million events, loading them into RAM to Replay will crash the system. We must design a Snapshot mechanism (saving a state snapshot every 100 events) to optimize load times.
*   **Mindset Shift:** Debugging becomes harder. You can no longer just open the DB to see the current number; you must trace the Event Logs chronologically to understand what happened.

## Conclusion
The journey from V1 to V2 is a transformation from a basic CRUD application into a true **Distributed Ledger**. Although significantly more complex, this is the only path for the `simulation-bank-platform` to securely process millions of transactions a day.
